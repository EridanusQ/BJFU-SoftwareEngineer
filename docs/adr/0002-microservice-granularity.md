# 0002 按限界上下文确定微服务粒度

Status: Accepted

Context: NekoCafé 需要支撑 38 家门店、预约高峰 5000 QPS、新门店零停机上线和跨门店运营分析。过细拆分会增加运维成本，过粗拆分会导致预约、订单、会员和运营看板互相牵制。

Decision: 以 DDD 限界上下文作为初始服务粒度，拆分会员、门店、预约、订单支付、猫咪档案、推荐、通知、运营分析 8 个服务。预约和订单支付为核心写服务，运营分析通过事件流构建读模型，推荐与通知作为支撑服务。

Consequences: 正面影响是核心服务可独立扩容、边界清晰、与 C4 L2/L3 对齐；负面影响是跨服务调用和分布式一致性复杂度提高；中性影响是早期可把低频服务合并部署但保留代码边界。

Alternatives Considered: 模块化单体，被放弃作为目标态，因为无法独立扩展预约热点；按数据库表拆服务，被放弃，因为会形成贫血服务和跨服务事务。
